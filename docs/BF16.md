# BF16 implementation notes

This records the experimental BF16 implementation contract. A separate BF16 runner
now runs; no full-model qualification or performance claim exists yet.
FP32 remains the default.

`src/bf16_kernels.rs` now provides experimental scalar and AVX-512BF16 dot,
unpacked linear and reusable packed linear operators. Tests cover real projection
dimensions, rows 1/2/4/8, output tails, FP64 mathematical comparisons and explicit
hardware subnormal behavior. The outputs remain FP32 until explicitly converted;
these operators alone do not reproduce the upstream BF16 graph. The
`examples/bf16_probe.rs` harness is intended for independent GPU operator fixtures.

The first 40 GPU projection cases cover 770,048 outputs, with all rows/channels
also compared to retained FP64 mathematical sums. Native BF16 direct/packed
operators have small FP32 errors but are not bit-equal GPU replacements, including
after a posthoc BF16 cast. These tests do not yet compare native GPU BF16-output
GEMMs or qualify the model graph. See `reference/bf16-isolated-probe-avx512.json`
and `reference/bf16-isolated-probe-scalar.json`.

The independently frozen `reference/bf16-local-contract-v1.json` uses only pinned
GPU, FP64 and blockwise GPU oracle results. Its assessment passes all 160 existing
FP32 accumulation checks and all nine normalization/gate checks. Eight norm/gate
checks are exact; the prefill learned norm differs at one value by one BF16 ULP.
The learned norm multiplies the FP32-normalized value by the promoted BF16 weight
before the one final BF16 cast. Native BF16-output matrix and attention checks
remain required; a posthoc cast comparison alone does not qualify the matrix path.

The initial full-graph BF16 policy is rejected: 47 stage bounds were at least as
large as the signal peak. A closer blockwise GPU oracle reproduces almost all
isolated attention values but still accumulates substantial hidden-state drift.
Neither policy is an acceptance gate. The new contract deliberately qualifies
equal-input operators and same-prefix logits/argmax, with exact free-running
CPU/GPU corpus outputs required separately. Full hidden-trajectory BF16 parity
remains unestablished. See `reference/bf16-policy-review.json`,
`reference/bf16-blockwise-trajectory-review.json` and
`reference/bf16-local-contract-assessment.json`.

The first native AVX-512BF16 graph emits the exact 17-token smoke output and owns
539,888,832 bytes of BF16 weight tensors. Direct native linear checks pass 40/40;
the unused packed variant passes 39/40. Attention passes 13/18 named output
checks, with sparse element violations despite passing RMS bounds. Same-prefix
logits pass 16/17 checks: every argmax agrees, but decode step 14 RMS error is
0.370306 against the frozen 0.302752 bound. The backend remains experimental;
none of these bounds has been widened.

A CPU-only replay isolates the sink boundary on the saved scaled-output failures.
The production expression reproduces all 832 saved values across 13 selected
heads exactly. Replacing only the raw attention value with the GPU value resolves
all 20 recorded scalar/AVX-512 scaled-output violations; replacing only LSE resolves
none. With both GPU arguments, CPU sink arithmetic produces the same final BF16
values on all 832 selected dimensions, despite an FP32 scale difference on one
head. This points investigation upstream of sink scaling on these cases; it does
not identify the QK/PV cause or qualify the complete attention operator. Sources,
executable and 3,328 replay inputs/outputs are preserved in
`artifacts/diagnostics/bf16-sink-replay-windows-v1`; see
`reference/bf16-sink-replay-windows-v1.json`. Reproduce with:

```powershell
python experiments/bf16_attention/analyze_sinks.py --output artifacts/diagnostics/bf16-sink-replay-new
```

The same standalone replay under WSL produces all 3,328 identical bit-pattern
records, after normalizing text line endings. This checks the selected sink
expression across platforms, not complete BF16 inference. See
`reference/bf16-sink-replay-cross-platform-v1.json`.

The separate saved-tile analysis traces four BF16 probability crossings to QK
scores/running maxima at the available independent-oracle boundary. Rust `exp2`
at the saved GPU arguments has no BF16 cast differences on those probes. These
are not captures of the fused GPU kernel's internals; exact fused intermediates
remain required. See `reference/bf16-attention-crossing-causality-v1.md`.

Layer 19 adds a distinct rounding case: its saved CPU raw quotient is only
1.72e-8 above a BF16 midpoint. Replacing one CPU tile's PV scalar with the FP64
dot of the same saved BF16 operands crosses back to the GPU raw value. This is
a sufficient counterfactual, not evidence that the GPU uses that reduction.
The independent GPU blockwise oracle already matches raw/scaled output while
sharing the CPU LSE bits. Actual fused accumulator/denominator capture is still
needed; see `reference/bf16-layer19-rounding-analysis-v1.md`.

## Pin dtype semantics before writing kernels

Use the actual pinned HF model and PyTorch 2.11.0 environment to export a BF16
trace on the same canonical inputs. The official engine keeps golden spatial
frequencies in FP32, while HF model-wide conversion casts that parameter to BF16.
These are different reference contracts; record which one the runner reproduces.

PyTorch 2.11 documents default RMSNorm epsilon in terms of the **opmath dtype**:
BF16, FP16 and FP32 inputs use FP32 epsilon. Do not automatically substitute
`bfloat16` machine epsilon at the input and Q/K normalization sites. This has now
been verified on actual and tiny inputs at widths 64 and 768 in the pinned
runtime: the result equals FP32 normalization followed by BF16 conversion.
The learned final norm still uses explicit model epsilon `1e-5`.
See [the versioned PyTorch documentation](https://docs.pytorch.org/docs/2.11/generated/torch.nn.RMSNorm.html).

Record and test these rounding boundaries independently:

- Weight conversion and image patch conversion before image projection.
- Input RMSNorm, QKV projection, Q/K RMSNorm and repetition.
- Temporal complex arithmetic in FP32, spatial frequency conversion/projection,
  rotary arithmetic in FP32 and the cast back to activation dtype.
- KV cache storage, attention accumulator/output dtype and FP32 log-sum-exp.
- Sink sigmoid scaling: attention's BF16 output is scaled using the higher
  precision LSE, then cast back before the output projection.
- Residual additions, FFN normalization and interleaved gate/up projection.
- Triton squared-ReLU gate: actual layer 0/12 probes match BF16 rounding after
  squaring and again after multiplying by the up branch. A single final rounding
  does not reproduce it; observed differences reached 128 on large layer-12 values.
- Final learned RMSNorm, vocabulary projection and argmax/tie handling.

Changing just weight storage does not reproduce BF16 GPU execution. That would be
a separate mixed-precision, weight-only variant and must be labeled accordingly.

## CPU implementations to compare

1. A scalar reference path using `half::bf16` for explicit conversion boundaries
   and FP32 accumulators. This establishes semantics, not the target performance.
2. Native AVX-512 BF16 vector dot products plus bounded batch/pre-fill kernels.
   Rust's [`_mm512_dpbf16_ps`](https://doc.rust-lang.org/core/arch/x86_64/fn._mm512_dpbf16_ps.html)
   is stable since Rust 1.89 and accumulates BF16 pairs into FP32. Runtime dispatch
   must check both AVX-512F and AVX-512BF16 before entering it.
3. Optional AOCL-DLP BF16 GEMM with once-packed weights. Compare realistic Falcon
   shapes and thread budgets against the Rust path, including batch-one decode.

Measure packing cost and resident memory separately from warm inference. Keep
softmax reductions and rotary arithmetic suitably precise, while honoring every
upstream cast. BF16 cache storage may halve bandwidth relative to FP32, but cache
layout, conversion overhead and token length determine the actual speedup.

Freeze a separate BF16 numerical policy using independent GPU/operator references
before CPU comparisons. Evaluate free-running OCR quality on the corrected corpus,
including long generations. Meeting the FP32 toy fixture's output is insufficient
for BF16 qualification. INT8 and INT4 experiments follow this stage.
